# User roles and permissions — known boundary

**Target role taxonomy: Not Verified.** One signed-in account could view selected organization/location/project/assignment/response records and the spatial viewers. The visible Program link returned `You do not have access to that page.` Assignment Edit was disabled in one observed state. Neither observation reveals role names, grant inheritance, record ownership, or authorization architecture. [ROLES_AND_PERMISSIONS.md](ROLES_AND_PERMISSIONS.md), [PAGE_MAP.md](PAGE_MAP.md)

IDS's [public technical article](https://www.immersiondata.com/resources/how-the-phygii-engine-works-a-technical-view-of-structured-property-intelligence) says the platform is designed with SSO, RBAC, logical client separation, and encryption [P-IDS-02](evidence/PUBLIC_SOURCES.md). These are vendor claims, not an audit of deployed controls or this account's exact grants.

For the independent app, start with explicit membership and resource-scope checks for `organization.read`, `location.read`, `project.read`, `media.read`, `spatial_asset.read`, `assignment.read`, and `response.read`; define separate mutation/manage/report/export capabilities only with product-owner approval. UI visibility is advisory; enforce every permission in server operations, Postgres RLS, and storage policies. Do not use user-editable metadata to authorize access; an authenticated role alone is not tenant authorization. [Supabase RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security). Test denied deep links and cross-tenant asset reads. No account administration was exercised in Phygii.
