# Independent application data-model proposal

This is a **new design proposal**, not Phygii's schema. It is derived only from the visible routes, labels, list relationships, and workflows in [DASHBOARD_FEATURES.md](DASHBOARD_FEATURES.md) and the live page dossiers. Fields not visible in the UI are design choices requiring product approval. No production data is to be imported without separate authorization.

| Proposed table | Core fields (suggested types) | Relationship / purpose | Evidence level |
| --- | --- | --- | --- |
| `organizations` | `id uuid`, `name text`, `created_at timestamptz` | Tenant root | Organization directory observed; field types proposed |
| `memberships` | `organization_id uuid`, `user_id uuid`, `role text`, `status text` | Explicit per-tenant access | Needed for safe independent design; role values not observed |
| `locations` | `id uuid`, `organization_id uuid`, `name text`, `address_text text`, `latitude numeric`, `longitude numeric`, `heading numeric` | Tenant-owned sites and map markers | Name/address/coordinates/heading visible; types proposed |
| `programs` | `id uuid`, `organization_id uuid`, `name text` | Optional grouping/filter | Program Filter and linked program seen; contents permission-denied |
| `location_programs` | `location_id uuid`, `program_id uuid` | Many-to-many grouping, if product rules require it | Hypothesis; UI does not prove cardinality |
| `projects` | `id uuid`, `organization_id uuid`, `location_id uuid`, `program_id uuid?`, `title text`, `capture_type text`, `status text`, `starts_at timestamptz?`, `ends_at timestamptz?` | Project lifecycle | Titles, status, location, program, dates shown; nullability/types proposed |
| `media_items` | `id uuid`, `project_id uuid?`, `location_id uuid`, `type text`, `storage_path text`, `captured_at timestamptz?`, `level text?`, `area text?`, `category text?` | Gallery/map assets | Type and metadata filters observed; storage structure proposed |
| `map_layers` | `id uuid`, `location_id uuid`, `kind text`, `name text`, `storage_path text?`, `level text?`, `created_at timestamptz` | Raster/vector layer catalog | Aerial and overlay lists observed |
| `spatial_assets` | `id uuid`, `organization_id uuid`, `location_id uuid`, `provider text`, `kind text`, `title text`, `level_id uuid?`, `provider_reference text?`, `storage_path text?`, `created_at timestamptz` | Provider-neutral catalog for tours, point clouds, BIM links, and native 360 assets | **Proposed schema** based on three distinct viewers and gallery [E-DT-01–04, E-MEDIA-01–02](evidence/OBSERVATIONS.md); no target table/API observed |
| `documents` / `document_versions` | IDs, project FK, title, category; version number, file path, created_at | Versioned project artifacts | Document cards and version list observed historically |
| `assignments` / `assignment_sections` / `tasks` / `questions` | IDs, project FK, ordered position, title, status and rule flags | Configurable checklists | Assignment tree/flags observed; exact rule semantics unknown |
| `responses` / `task_responses` / `answers` | IDs, assignment FK, respondent FK, status, timestamps, typed answer payload | Work execution and progress | Counts/status visible; answer schema not observed |
| `collections` / `collection_items` | IDs, organization/owner FKs, title, visibility, item reference | User-curated groupings | Empty collection UIs and privacy filter visible; contents unknown |
| `audit_events` | ID, actor, tenant, entity/action, timestamp, redacted metadata | Security and mutation trace | Proposed security requirement, not observed product feature |

Design rules: use explicit tenant foreign keys; enforce uniqueness for membership pairs and ordered child positions; index foreign-key columns and tenant FK + status/name for list filters, location geography only if map scale warrants it, and `(assignment_id, status)` for responses. The `uuid` examples above are placeholders for exposed IDs, not a finalized key strategy: choose sequential `bigint identity` for single-database internal tables or time-ordered UUIDs for distributed/exposed IDs after confirming extension support and migration needs. Define status transitions and count formulas with product stakeholders before implementation; the UI alone does not establish them. Separate uploaded binary content into private object storage with metadata rows; avoid storing sensitive answer contents in logs. These key/index considerations follow Supabase's Postgres design guidance; they were not inferred from the target app.

Enable row-level security on every exposed table; tenant membership and resource scope must be checked in each read/write policy. An authenticated database role alone is not tenant authorization. Use immutable audit records for state-changing operations and test cross-tenant denial. This follows [Supabase's RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security) and [Storage access control guidance](https://supabase.com/docs/guides/storage/security/access-control), not an observation of Phygii's security design.

For the proposed `spatial_assets` table, provider references should be opaque and server-controlled. A view instruction should be issued only after membership/resource checks; never put long-lived provider credentials in browser-visible metadata. Store asset provenance and conversion status for independently uploaded point clouds and rasters. Whether IDS does any of this is unknown; [INTEGRATION_CATALOG.md](INTEGRATION_CATALOG.md) records only observed display boundaries.
